# منصة روافد — Central Theme Architecture

## الهدف

الحفاظ على منصة ديناميكية قابلة للتوسع مع أقل تغييرات ممكنة في طبقة البيانات وأقل حركة على Supabase، مع جعل العرض مركزيًا ومؤسسيًا وقابلًا للتطوير دون نسخ CSS أو مكونات بين الصفحات.

## العقد المركزي

- الاسم الرسمي في الواجهة: **منصة روافد**.
- `app/rawafid-theme.css` هو نقطة الدخول العالمية الوحيدة للثيم.
- القيم البصرية الجديدة تستخدم Semantic Tokens تحت `--rf-*`.
- ملفات V3 الحالية تبقى محملة من نقطة الدخول المركزية أثناء الانتقال، لذلك لا يوجد كسر جماعي للصفحات.
- أي صفحة أو Module جديد يعيد استخدام المكونات والقيم المركزية ولا يضيف Global CSS import إلى `app/layout.tsx`.
- ألوان القطاعات Accent فقط، ولا تغير الهوية المؤسسية العامة.
- `lib/theme.ts` هو مصدر الاسم المؤسسي واختصاره وخريطة ألوان القطاعات النصية القديمة.

## ترتيب الطبقات

1. Compatibility foundations (ملفات V3 الحالية بالترتيب الأصلي)
2. Semantic Rawafid V5 tokens
3. Global application shell
4. Shared public components
5. Responsive and accessibility hardening
6. Reduced-motion and print contracts

## طبقة V5 المؤسسية

- الواجهة العامة تبدأ من نية الزائر، ثم تقوده إلى المعرفة أو الدليل أو الدعم، ولا تعرض مصطلحات البنية التقنية.
- `components/rawafid-mark.tsx` هو الرمز البصري الموحد للرأس والتذييل والحسابات ولوحة الإدارة وأيقونات PWA.
- `lib/public-content.ts` يقرأ أحدث المحتوى المنشور عبر المفتاح العام وRLS مع إعادة تحقق دورية؛ لا توجد مفاتيح سرية أو استعلامات خدمة في الواجهة العامة.
- `lib/content-templates.ts` يعرّف نقاط بداية مشتركة للمدير والمختص، بينما يبقى نموذج المحتوى وإصداراته وسير المراجعة واحدًا.
- `/admin/verification` يجمع إشارات طوابير المختصين والمراكز والمجتمع والمستندات في واجهة أولوية واحدة، لكن تنفيذ القرارات يبقى داخل RPC ومسارات المراجعة الآمنة القائمة.
- V5 لا يضيف Schema أو سياسة RLS جديدة؛ التحسين بصري وتشغيلي فوق الحدود الأمنية الموجودة.

## قواعد منع التكرار والكود الميت

- لا يُنشأ ملف CSS عالمي جديد ما لم يكن Module مستقلًا وواضح الحدود، ويجب استيراده من `rawafid-theme.css` فقط.
- لا تُكرر ألوان أو Radius أو Shadows جديدة بقيم Hex داخل المكونات إذا كان لها Token مركزي.
- لا تُنشأ نسخة ثانية من Header/Footer/Card لمجرد اختلاف قطاع؛ استخدم Props/Accent.
- لا تُنقل بيانات تصميم ثابتة إلى Supabase.
- لا تُنشأ بيانات تجريبية في Supabase لأغراض العرض.
- لا يحذف أي ملف Compatibility قبل التأكد بالبحث والاختبارات أنه لم يعد مستخدمًا.

## استراتيجية الأداء

- Root Layout يحمل نقطة Theme واحدة بدل عشرات Imports المباشرة.
- تحسين بصري لا يضيف Client JavaScript ما لم توجد حاجة تفاعلية حقيقية.
- القطاعات العامة تستخدم Cache/Revalidation الموجود في Adapter.
- يتم الحفاظ على Server Components حيث لا نحتاج تفاعل Client.
- أي تعديل يجب أن يجتاز TypeScript + ESLint + Architecture Contracts + Next Build + OpenNext Build + Wrangler Dry Run، ثم Smoke وLighthouse على بيئة النشر.

## استراتيجية Supabase

الثيم لا يغيّر Schema ولا RLS ولا البيانات. اختلافات ألوان القطاعات القديمة مثل `blue` و`teal` تتم تسويتها في Adapter الواجهة عن طريق `resolveSectorAccent()` بدل Update جماعي في قاعدة البيانات.

## التوسع

الهدف أن إضافة قطاع، قسم، محتوى، مختص أو مركز لا تحتاج CSS أو Route جديدًا عندما يغطيها القالب الديناميكي القائم. الثيم مسؤول عن العرض، وSupabase مسؤول عن البيانات والحالة والصلاحيات.
