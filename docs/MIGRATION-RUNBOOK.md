# Rawafid — Legacy Content Migration Runbook

## الهدف

نقل المعرفة والبيانات المفيدة من المستودع القديم `khaledaltheeb/healthrenewal.org` إلى منصة روافد الجديدة دون نقل الثيم القديم أو CSS/JS/Layouts أو أخطاء البنية القديمة، ودون نسخ ولصق الصفحات كما هي.

## القاعدة الأساسية

كل موضوع يُعامل كوحدة معرفية Canonical واحدة. جميع النسخ والطبقات والصفحات المتقاربة تاريخيًا تُدرس معًا، ثم تُبنى صفحة جديدة من الصفر داخل CMS الجديد بعد استخراج أفضل المعلومات الصحيحة وإزالة التكرار والحشو والملاحظات الداخلية.

## ما يُستبعد نهائيًا من النشر

- المحادثات أو الملاحظات الخاصة بين المالك والمساعد/الوكلاء.
- خطط العمل، تعليمات التنفيذ، قوائم المهام، ملاحظات QA، نصوص TODO/FIXME، وملاحظات التطوير الداخلية.
- رسائل مثل «سنضيف لاحقًا»، «يجب أن نبني»، «المطلوب من الوكيل»، أو أي صياغة تصف خطة العمل بدل تقديم معرفة للمستخدم.
- النصوص المكررة، القوالب القديمة، تحذيرات الاختبار، رسائل النشر، وسجلات CI/التوليد.
- أي Claim غير مدعوم أو تعريف غير مطابق للمصدر الرسمي/المهني المناسب.

## سياسة التحذيرات والتنبيهات

روافد ليس موقعًا مبنيًا على التخويف أو التحذير المتكرر. لا تُكرر عبارات إخلاء المسؤولية داخل كل فقرة، ولا يُحجب المحتوى التعليمي المفيد لمجرد أنه مهني أو متقدم.

تُستخدم تنبيهات مختصرة ومحددة فقط عندما تكون لها ضرورة فعلية: خطر فوري، إجراء قد يسبب ضررًا، تشخيص ذاتي غير مناسب، دواء/تدخل يحتاج إشرافًا، أو متطلب قانوني/ترخيصي حقيقي. المعلومات التعليمية، الشروحات، النماذج التدريبية، والممارسة التعليمية للمتدربين والمختصين تبقى متاحة ضمن حدود قانونية ومهنية صحيحة.

## معيار الصفحة الجديدة

- صفحة واحدة Canonical لكل مصطلح/موضوع، مع Redirects للنسخ القديمة ذات الصلة.
- لا يقل المحتوى المستهدف عادة عن 1500 كلمة عربية مفيدة إذا كان الموضوع يحتمل ذلك، ويسمح بالتوسع دون سقف ثابت.
- يمنع إطالة الصفحة للوصول إلى رقم شكلي؛ الجودة والتغطية أولًا.
- H1 واحد واضح، ثم H2/H3 منطقية حسب بنية الموضوع.
- تعريف رسمي أو مهني دقيق من المصدر الأصلي/المؤسسة الرسمية/الإرشاد المرجعي المناسب.
- شرح تقريري مباشر يسهل على المستخدم ومحركات البحث ونماذج الاستخراج فهم الحقائق: «يُعرّف…»، «يرتبط…»، «السبب…»، «النتيجة…» عندما تكون الصياغة صحيحة علميًا.
- أسئلة FAQ حقيقية تغطي نوايا البحث: ما هو؟ لماذا؟ ما الأسباب؟ كيف يظهر؟ متى أطلب مساعدة؟ ما الفرق؟ كيف أتعامل؟ دون تكرار متن الصفحة حرفيًا.
- فصل واضح بين الحقائق الراسخة، الأدلة المحدودة، الاختلاف بين الإرشادات، والمعلومات التي تحتاج تحديثًا دوريًا.
- صور داخلية وصورة بارزة عند الحاجة مع Alt دقيق.
- مراجع موثوقة وروابط HTTPS، واسم المؤلف/المراجع وتاريخ آخر مراجعة للمحتوى الطبي/YMYL.

## SEO لكل صفحة

- Keyword/Entity رئيسية + مرادفات ومصطلحات دلالية دون حشو.
- Search intent محددة.
- SEO Title وMeta Description فريدان.
- Canonical صحيح.
- Structured Data متوافق مع نوع الصفحة؛ FAQPage لا يُستخدم إلا للأسئلة الظاهرة للمستخدم، وMedical schema حيث يكون مناسبًا.
- Breadcrumbs وروابط داخلية إلى القطاع/القسم/المحتوى المرتبط.
- الحفاظ على قيمة الروابط القديمة عبر Redirect mapping بدل إنشاء صفحات متطابقة.
- لا يتم نقل GA/GTM «لكل صفحة» كنسخ كود متكررة؛ القياس يُثبت مركزيًا في Shell/Tag Manager الجديد ثم تستخدم الصفحات نفس طبقة التحليلات مع أحداث وMetadata صحيحة.

## آلية اكتشاف ودمج النسخ

1. بناء Inventory لكل الملفات/URLs الحالية ثم مراجعة تاريخ Git عند الحاجة.
2. استخراج العنوان، H1، slug، canonical، metadata، النص، الروابط والمراجع من كل نسخة.
3. إنشاء Fingerprints نصية ودلالية لاكتشاف التطابق والتشابه العالي.
4. تجميع Clusters حسب الموضوع/الكيان/المصطلح، وليس حسب المجلد القديم فقط.
5. تصنيف كل مصدر داخل الـCluster: أساسي، نسخة أقدم، توسعة مفيدة، تكرار، ملاحظة داخلية، أو مادة يجب استبعادها.
6. إعداد Brief موحد للصفحة الجديدة.
7. إعادة بناء الصفحة داخل CMS من الصفر.
8. مراجعة علمية/تحريرية/SEO/Accessibility ثم اعتماد/جدولة/نشر.
9. تسجيل كل URL قديم ووجهته الجديدة في Redirect map.

## الموسوعة

كل مصطلح مستقل يجب أن يحصل على صفحة مستقلة إذا كان يمثل كيانًا/مصطلحًا بحثيًا حقيقيًا. لا تُنشأ صفحات رقيقة لمجرد زيادة العدد. صفحات الموسوعة تُبنى بالحد الكافي من التعريف، الفروق، السياق، العلامات/الخصائص إن وجدت، الأسباب/العوامل، التطبيق العملي، الأسئلة الشائعة، المراجع، والروابط الداخلية.

## التشغيل على دفعات

لا يُنشر عشرات الآلاف دفعة واحدة. كل دفعة تمر: Inventory → Dedupe → Rewrite → Review → QA → Publish → Redirects → Post-publish validation. الترحيل Idempotent ويجب أن يدعم Dry-run وRollback وعدم إنشاء نسخة ثانية لنفس الصفحة عند إعادة التشغيل.

## الاستمرارية بين المحادثات والوكلاء

المرجع التشغيلي هو هذا الملف مع `docs/MIGRATION-PROGRESS.md`. أي محادثة/وكيل جديد يبدأ بقراءتهما أولًا ثم يكمل من آخر Batch موثق. لا يعتمد على الذاكرة الشفهية وحدها.
