# Assessment Lab / «اختبر نفسك» — persistent implementation contract

This file is operational guidance for future maintainers/agents. It is not user-facing content.

## Product goal
Build the strongest responsible Arabic self-check library possible without pretending that local tools are diagnostic tests. Preserve every valid historical route/content item, enrich rather than delete, and never replace evidence with generic filler.

## Current release scope: 70 public routes only
The active product scope is **70 published assessment routes only** until an explicit future decision changes it.

Current production composition:
- **60 Rawafid-original monitoring/self-reflection tools**.
- **10 source/rights routes** for notable external instruments, documenting source, population, Arabic-version status, reuse rights and scoring status.

Total active scope: **70 public routes**.

Do not add route 71 or expand the public catalog during the current phase. The priority is to make the existing 70 routes complete, distinct, scientifically responsible, useful, accessible, indexable, and production-stable.

A previously prepared 150-route roadmap may remain in the repository as a **deferred future backlog only**. It is not an active publication target, must not drive current UI counts, must not trigger mass-generation, and must not be interpreted as permission to publish additional routes. Future expansion requires an explicit product decision plus the same scientific and quality gates defined below.

## Absolute scientific completeness rule
A working page with questions is NOT a complete assessment.

No Rawafid-original tool may be described internally or publicly as scientifically complete until it has all of the following documented:
1. construct definition;
2. intended population;
3. intended use and explicit non-use cases;
4. reference/recall period;
5. domain/axis map;
6. item rationale and coverage map;
7. response scale whose semantics match the wording of each item;
8. plain-Arabic language review and comprehension review;
9. content-validity review by relevant experts;
10. privacy and data-flow statement;
11. interpretation rules and boundaries;
12. functional-impact guidance;
13. safety escalation rules;
14. professional referral route;
15. scientific references supporting the construct and domain design;
16. version number and change log;
17. declared validation stage.

A generic question template alone can never satisfy this standard.

## Response-scale rule
Do not use one mixed response scale across items that ask different kinds of questions.
- Frequency items must use a frequency scale.
- Degree/intensity/extent items must use a degree scale.
- Direct yes/no experience items must use a yes/no-style response architecture or be rewritten.
- The wording and response options must be semantically compatible in Arabic.

## What “validated” means
`validated` is an empirical status, not an editorial status.

A tool may be labeled validated only after an appropriate empirical program, which may include depending on the construct:
- content validity;
- cognitive interviews/comprehensibility testing;
- pilot data;
- item analysis;
- dimensionality/factor structure;
- internal consistency where applicable;
- test-retest reliability where applicable;
- convergent/discriminant/criterion validity where applicable;
- differential item functioning or measurement invariance where relevant;
- criterion-based cutoff calibration only when justified;
- a public technical manual/version record.

Editorial review, expert opinion, a functioning UI, or a plausible set of questions is never sufficient by itself to claim psychometric validity.

## Development maturity states
Every Rawafid-original tool must have exactly one maturity state:
- `concept`
- `item-development`
- `expert-review`
- `cognitive-interview`
- `pilot-ready`
- `pilot`
- `psychometric-analysis`
- `validated`

No tool may jump directly from concept/editorial build to validated.

## What “better than a licensed test” is allowed to mean
Rawafid may build an independent tool that is better in **language clarity, accessibility, Arabic/RTL UX, contextual explanation, functional follow-up, privacy, safety escalation, breadth of domains or user usefulness**. Do not claim that it is psychometrically superior, more valid, more reliable, more sensitive or more accurate than an established instrument until a direct empirical comparison supports that claim.

## Restricted-instrument rule
When a known measure is licensed/restricted, the current 70-route phase does not add a replacement instrument merely to increase route count. Source/rights pages must remain transparent about attribution, Arabic-version status, scoring status, and reuse rights. Do not reproduce protected item wording, translations, item order, response architecture, scoring keys, cutoffs, proprietary subscale names, or reverse-engineer the original instrument.

## Non-negotiable rules
1. Do not delete, hide, orphan or silently replace an existing published assessment route.
2. Preserve exactly the current 70-route public scope unless the product owner explicitly changes it.
3. Every public page must be useful, unique and indexable unless there is a documented legal/safety reason not to index it.
4. Local Rawafid monitoring tools are NOT validated diagnostic instruments unless a completed validation program says otherwise. Do not invent cutoffs, diagnoses, severity bands, norms or psychometric claims.
5. Known instruments must remain clearly attributed to their source. Do not copy protected items, translations or scoring logic unless reuse rights and the exact Arabic version are verified.
6. Answers must not be stored or transmitted unless the product direction is explicitly changed after a privacy review. Current contract: no server submission, no account storage, no localStorage, no sessionStorage.
7. Language must be direct, simple Arabic. Avoid obscure clinical jargon in questions. Each item should be understandable without explanation.
8. Questions must measure/observe a concrete experience, context, functional effect, protective factor or support need. Avoid vague filler and duplicated items.
9. Do not collapse heterogeneous axes into one percentage. Summaries may organize observations but must not masquerade as psychometric scoring.
10. Every tool must include purpose, reference period, privacy statement, interpretation boundary, when to seek professional help, and a route to specialists/guided assessment.
11. Safety escalation must be visible for imminent self/other harm, violence, severe loss of reality testing, acute medical symptoms, or rapid functional deterioration.
12. Public copy should state: «تمت المراجعة من قبل فريق روافد», while clarifying that review does not convert a local monitor into a validated psychological test.
13. Apply Rawafid comprehensive SEO: self-canonical URL, index/follow for reviewed public pages, sitemap inclusion, useful titles/descriptions, structured breadcrumbs, internal links, no keyword stuffing or doorway pages.
14. No current-phase change may raise the public Assessment Lab count above 70.

## Methodology anchors
At implementation/review time, use up-to-date authoritative methodology, including where applicable:
- COSMIN for content validity and measurement-property methodology;
- FDA guidance for patient-reported outcome instrument development and use context;
- HealthMeasures/PROMIS methodology for modern item-bank, dimensionality and DIF concepts.

These are methodological anchors, not permission to copy proprietary item content.

## Current completion priority
Work only on the existing 70 routes and their shared system:
1. verify all 60 Rawafid tools have tailored, non-duplicated 16-item banks and four coherent axes;
2. verify every Rawafid tool has a complete scientific dossier and traceable references;
3. audit Arabic clarity, item/response semantic fit, safety wording and functional usefulness;
4. audit all 10 source/rights routes for current authoritative source and rights wording;
5. improve UX/accessibility/RTL/printing without storing or transmitting answers;
6. verify SEO, canonical, indexability, sitemap inclusion and internal linking for all 70;
7. run assessment contracts, typecheck, lint, architecture/build and production smoke checks;
8. publish only after those gates pass, then verify the live production routes.

## Quality gate before merge/deploy
Run the assessment-lab contracts plus repository architecture/build checks. Reject publication if any of the 70 routes is lost, an extra assessment route is accidentally published, a detail canonical points to the hub, a reviewed route is noindex, answers are persisted/transmitted, fabricated scoring reappears, response semantics are mismatched, scientific-completeness metadata is missing for tools claiming completion, or a restricted instrument is reproduced without verified rights.
